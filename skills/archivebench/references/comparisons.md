# Compare quality, space and time

## Quick comparison

Before launching or resuming, read [wait-what](wait-what.md) and show a concise brief from the saved config, plan and local discovery. This disclosure is required even when execution is already authorized; reuse that authorization rather than adding a confirmation gate.

**Availability table:** one row per discovered supported encoder, with codec, exact encoder name, CPU/GPU and device, availability evidence, and selected/not selected with reason. Distinguish FFmpeg-listed, excluded by manufacturer/FFmpeg evidence, successfully tested for this device/format, failed and unknown. Include relevant requested encoders that are missing or lack an adapter. Listing or manufacturer support is not proof of runtime compatibility. Report known exclusions without retrying impossible combinations or silently reducing chroma/bit depth. Use current discovery results; label historical checks as historical.

**Test-plan table:** one row per selected encoder/format, with clip label and interval, format policy, exact speed/quality controls, setting count, timing repeats, planned encode count, estimated encode-plus-score time, and estimate basis/confidence. Name any additional preparation, probes, tuning, validation or review work outside that count. For adaptive refinement, show bounds rather than an exact count. For resume, distinguish completed work from pending work.

End the brief with total planned work, approximate total elapsed time or unknown, the separate time allowance, scratch needs, stop/resume behavior, and deliverables (report, visual pairs when ready, reusable starting presets). Estimates must use comparable local measurements and include preparation/scoring/review overhead. Without evidence, write **unknown until measured**; a ten-minute allowance is not a ten-minute ETA. Update estimates after completed measurements. State that original files remain intact and that the user decides visual acceptance.

**Format disclosure:** in both plan and results tables, each row must show source → output chroma and explicitly say **preserved** or **reduced** (for example `4:2:2 → 4:2:0 — reduced`). Also show bit depth and dimensions, with any change named. Resolve “source” from actual metadata; split mixed-source policies into distinct rows. State reductions in the opening summary, not only a footnote. Preserve source chroma unless the user's agreed scope explicitly includes conversion; ask only when that choice is unresolved. Keep compression and format conversion distinct when interpreting savings. A VMAF score alone does not establish chroma fidelity.

1. Use `archivebench setup --strategy fixed --config CONFIG`. Select CPU/GPU implementations or `all` supported installed candidates, explicit formats, a representative section (default five seconds), and a separate time allowance (suggest 30 minutes). Listed encoders still need a successful encode on this hardware and format. Done when saved sources, intervals and encoders match the user's choices.
2. Inspect `fixed_settings` and run `archivebench plan CONFIG`. Default to two encoder-specific quality settings and one timing repeat. Quality numbers are not equivalent across encoders. The first scene tests one setting per encoder before further settings; extra scenes explore the measured frontier. Preserve dimensions, frame rate, bit depth and chroma unless a conversion is explicitly selected. Done when the plan exposes settings, encode count, scratch needs and known/unknown estimates.
3. Run `archivebench benchmark CONFIG --output RUN`. Preparation, hashing, encoding, scoring and review preparation consume the allowance. Scores are observations, with no target search. Use `archivebench status RUN` and canonical `results.json` for completed, failed and unfinished work. Verify process identity before treating a checkpoint as running. Done when execution finishes, reaches its allowance, is paused, or encounters an actionable blocker.

Run without competing editing/export work for meaningful timing. Record automatic encoder threading and scoring calibration; claim throughput improvements only from measurements. Timeouts are unfinished evidence, not proof of incompatibility. Preserve paused runs. Resume grants another allowance only when authorized; changed settings, sources or toolchain require a new output folder. Keep older evidence separate.

## Interpretation and review

Quick mode delivers the measurements report with detailed browser assets deferred. Interpret it first; use exact native comparison directly, or `review prepare --results RUN/results.json --trial ID --seconds 120` for a selected candidate's browser stills and previews. Explain and budget that separate work. Original previews are shared within the run. Request `review_mode: "full"` only when automatic frontier visuals are wanted; measurements still appear first. Inspect asset status instead of assuming preparation succeeded.

Read `results.json`, `summary.md` and `report.html`. Compare matching sections and explicit formats. Explain observed quality, video savings versus source, encode time and Pareto choices. Video-only projections exclude retained audio and other streams. Attribute differences to actual compared settings, rather than invented additive percentages for codec, speed and quality. VMAF is a model score, not a percentage of retained quality.

Offer successful quick measurements as **measured starting points**, with sample scope, missing coverage and estimates visible. Export portable presets from the report for later folders; visual acceptance and fresh validation remain separate evidence. Partial reports leave unfinished tests unfinished. Keeping originals is a valid choice.

Use `archivebench review inspect --results RUN/results.json` for trial IDs and exact aligned pairs. `review launch --results RUN/results.json --trial ID` opens optional video-compare. Browser conversions and stills are aids, not proof of source bit-depth or chroma fidelity. Native display conversion and monitor fidelity also matter. The viewer is silent.

After the user reviews a pair, `review record --results RUN/results.json --trial ID --decision accept --reviewer NAME --method native` records their attestation. Rejections can add `--objections "0.5,1.2" --note TEXT`. Opening the viewer alone is not acceptance. Regenerate presentation with `archivebench report RESULTS` when needed.

Completion: offered settings have measured evidence and scope; uncertainty and the user's choice are explicit. For future folders, read [preset reuse](preset-reuse.md); for requested encoding, read [archive jobs](archive-jobs.md).

## Analyze every report and propose the next step

1. Read canonical results and account for all planned tests, failures, missing review assets and evidence scope. Present format-explicit results with size/savings, encode time, mean VMAF and low-tail scores when available. Explain fastest, smallest and quality tradeoffs only for comparable sections. Done when the user knows what the run establishes and what remains unknown.
2. Separate encoding, scoring, shared preparation and review/report time. Retain measured timings in the run; use them as historical baselines for subsequent estimates, naming source run, hardware, section, controls and format. Count shared preparation once. For a new quality value or format, provide a clearly provisional range, not a measured promise. If a phase has no separate timing, label the gap; avoid assigning aggregate overhead to one operation. Done when estimates have an explicit basis and excluded/unknown work is visible.
3. Recommend the smallest next experiment that resolves a decision. Provide a table with exact encoder/settings, section, source → output chroma, test count, reason, expected decision and approximate time/basis. Favor one changed variable and existing evidence over broad sweeps. Consider preserved-chroma comparisons, a neighboring quality setting, or a second difficult scene based on actual gaps and user visual feedback. Exact VMAF searches are optional, not the default response to a score gap. Distinguish a proposed test from an authorized run.
4. End with a concrete recommendation: review named moments, run the proposed small follow-up, save an accepted starting preset, or stop with sufficient evidence. A completed report requires agent interpretation, not just a link. More data is useful only when it can change the user's choice; formatting complaints alone do not justify more encodes. Record review-generation bottlenecks separately from codec performance and label proposed tool optimizations as unimplemented until verified.

## Optional target refinement

Use `setup --strategy tune` when the user requests exact-target refinement. Legacy configurations without a strategy also tune. Inspect targets, tuning sections, separate fresh holdouts, screen/pilot work, repeats, scratch and budget before running. A tuning section cannot also be its fresh holdout. Multiple targets can add substantial work despite shared measurements.

Qualify target-based recommendations only with complete required tuning and fixed-setting fresh-validation coverage. Report failed probes, below-target scenes and missing validation. Metric passes remain separate from visual acceptance and editor reopening/relinking. Expand only to resolve an unanswered choice within the authorized scope.
